# Roadmap proposals and follow-up research, 2026-11-06

Archived verbatim from `docs/UNITY-CAPABILITY-ROADMAP.md` on 2026-11-11 (approved trim: current content stays, the rest moves here, nothing deleted). Read only when the current docs lack something.


## Next implementation slice (proposal)

1. Animation Rigging + a generic body/joint/contact/force adapter.
2. A generated creature reaches for and carries a generated object; object mass, target, grip and gravity are recipe parameters. Contact emits an event that Feel can render.
3. Change those values during play through the same operations from world tools, browser fields and Script; save/reload and inspect actual measured results.
4. Add navigation, spline geometry and a single Obi material test as separate milestones.

Each adapter must create/update/remove bindings during play, expose supported parameters and part roles, report realized state/failures, and serialize enough configuration to rebuild. Define who writes each root/limb/material simulation, and budget generation, mesh rebuilding, collider cooking and solver load. A package's runtime API is evidence of feasibility, not proof that our generated rigs and target devices already work.

## Follow-up decisions: peaceful runtime creation

Destruction is outside the current product scope. Do not add fracture/cutting tools. Digger is too heavy and Archimatix too complex for the desired approach.

- **Playables:** a runtime API for dynamically constructed animation/audio graphs, mixing and weights. Use as a low-level presentation adapter. No preauthored Animator Controller is required for every generated combination. Available node implementations still need to ship with the app.
- **Timeline 6.6:** already installed. Local runtime source exposes TimelineAsset.CreateTrack and TrackAsset.CreateClip. Runtime-created timelines can coordinate shots, audio and animation. Keep branching gameplay rules in Flecs. Persist the recipe/clip references/bindings and rebuild the graph, rather than relying on Editor AssetDatabase saving. Define cancellation and transform ownership when interactive control interrupts a sequence.
- **MudBun versus Obi:** MudBun deformations, animated brushes, SDF rendering and particle meshing can cover many visual squish, slime and liquid-like effects. Boing can drive secondary brush motion. These do not automatically provide rope constraints, cloth, soft-body collision or incompressible liquid simulation. Defer Obi until those physical consequences are required; nothing needs buying now. Particle meshing and SDF collision textures are additional MudBun capabilities, not a full fluid solver.
- **Controllers:** CharacterController is already the compiled ground-motor capability. Runtime recipes select/configure controllers, including for NPCs. Floating/swimming/vehicles need different motor behavior; avoid assigning every creation a capsule by default.
- **2D:** the Physics2D module is already present. Add 2D Animation/Sprite Shape/Tilemap authoring packages only for selected sprite, bone, contour or tile features. 2.5D can use orthographic presentation with existing 3D physics; 2D and 3D colliders do not automatically interact. Runtime sprite construction is distinct from Editor sprite slicing/PSD import.
- **ProBuilder:** a real runtime mesh-creation/editing API exists. Candidate for polygonal forms/extrusions/hard-surface objects beyond MudBun or the current spline/building tools; the Editor UI does not ship automatically. No package has been added.
- **VFX:** start with runtime-configured ParticleSystem, trails, lines, decals and existing FluXY/MudBun effects. VFX Graph is useful for larger GPU effects, but ordinary player use selects already compiled graphs and modifies properties/events; it does not compile arbitrary new VFX graphs/shaders during play. Verify target graphics API/device support before making it required.
- **Audio:** installed MMSequence/MMSequencer/MMSoundSequencer support note/timestamp data and sound triggering. A runtime adapter can construct a pattern, choose clips, adjust pitch/filter/mix and attach spatial sources. Sequencing alone does not synthesize instruments, animal voices or arbitrary sounds. Optional AudioClip PCM generation can provide a compiled synthesis palette; recorded/downloaded sound is another source. For tight musical timing use Unity DSP scheduling rather than frame-timed Flecs events for each sample/beat.
- **Remaining execution capabilities:** materials/lighting/environment controls; drawing/painting into textures and lightweight mesh/height-field sculpting; attachment/grip/contact/sensing; buoyancy/flow; navigation; reusable device input and haptics. Save binary image/audio/mesh assets separately and refer to them from recipes. Continue using Flecs for rules, objectives, reactions and state.

## Adaptive worlds, handles, shaders, music and portable execution

Research follow-up, 2026-11-06; no additional package/runtime integration performed.

- **Terrain:** the Jason Booth product found is MicroVerse (assuming this is the user's "MicroWorld"). Do not rely on an unsupported runtime port as the foundation. MicroSplat Runtime Procedural Texturing explicitly supports shader-side live height/slope/noise rules; it shades terrain, rather than generating all terrain changes. It requires the appropriate URP integration. MapMagic 2 is a runtime terrain-generation candidate, not a verified drop-in drag-road system or Ecaty integration. No current off-the-shelf replacement has been verified against this project's shipped build.
- **Road adaptation:** treat a spline as a reusable modifier with a width, falloff, height profile, surface and exclusion mask. Its affected region updates ground shape, material masks, vegetation placement, colliders and navigation through explicit adapters. Recompute from base data plus modifiers so undo/removal restores the prior ground; do not repeatedly deform last frame's result. Existing Spline Mesher can supply geometry. A small height-field/mask adapter is still missing even if MicroSplat supplies the appearance. Regeneration should be local and debounced while dragging.
- **The Visual Engine:** worthwhile for unified wind, wetness, seasonal appearance and vegetation interaction. Shader execution and dynamic visual controls are distinct from Editor prefab conversion. Generated Broccoli/MudBun meshes must supply compatible materials, attributes and masks; conversion presets alone do not establish this. Inspect the imported version and prove runtime-generated content in a Windows player before adopting. It does not provide an entire sky/weather simulation or automatic physical wind forces.
- **Runtime shaders:** Amplify is an Editor authoring tool. Build shader families/required variants ahead of shipping; runtime material recipes change textures, masks, color, layering, emission, wetness and deformation parameters. Runtime-generated textures expand variety. Arbitrary new ASE/Shader Graph/HLSL compilation is not a supported general portable player workflow. A bounded interpreted material graph is possible, but would be another shader system to implement and profile; no convincing need yet.
- **VFX:** ParticleSystem is directly configurable at runtime. VFX Graph effects run in a player, accept parameters, events, meshes and textures, and can be spawned/rebound during play. The graph implementations/shaders are prepared at build time. Verify mobile graphics API/budget; effects do not imply physical fluid simulation.
- **Music:** Maestro Pro explicitly provides live MIDI generation/editing, SoundFont synthesis/loading and musical callbacks; it is a strong Unity-ready option. Maestro Free already supports real-time note generation and an included SoundFont, sufficient for a first prototype. Feel remains the general feedback/sequence layer. These solve different needs. MIDI/SoundFont instruments do not cover every environmental or creature sound.
- **Open audio alternatives:** MeltySynth (MIT C#, .NET Standard 2.1) generates PCM from SoundFonts; Unity still needs an audio-thread-safe output/command bridge and target testing. TinySoundFont (MIT C/C++) is a small native alternative with the same integration work rather than a ready-made Unity toolkit. Neither is established as better than Maestro for development effort; audio quality also depends on the sound bank. SoundFont redistribution permissions are separate from the synthesizer source license.
- **Handles:** expose controls as target plus property/part, coordinate space, constraints, range and action. The same adapter can support brush pivots, spline points and object transforms. Flexalon supplies arrangement, not generic transform manipulation. Runtime Transform Gizmos is an optional established manipulation API; start with direct grab/point handles if standard editor arrows conflict with the product. Changes update Flecs-authoritative recipe data through preview/commit/undo. Define temporary drag ownership so a motor/physics solver does not fight the handle; release can produce a user-authored event such as entering water. No AI is needed per drag frame.
- **Weather:** the owned audit includes UniStorm and Weather Maker. UniStorm's publisher documents Unity 6/URP/Render Graph support and a runtime API; inspect/import one weather solution rather than stacking both. Flecs supplies world-scoped time, cloud/rain/wind/temperature intent; the adapter renders it. TVE wetness/wind and Crest waves require explicit coordinated bindings. Rain visuals do not automatically create puddles, rising water or wet-ground friction. Multiple miniature worlds may require scoped effects because global sky/weather systems often assume a single environment.
- **Complex behavior:** BehaviorTree.CPP (MIT C++) can create trees from XML at runtime using registered operations. Evaluate as an optional executor for reusable hierarchical/parallel/cancellable tasks. Flecs retains entities, facts, parameters and effect commands; the executor owns task execution status, exposed for inspection. Avoid copying the whole world into a blackboard. AI may compose new trees from shipped operations; new native operations remain compiled. BehaviorTree.CPP does not add physical abilities or a general planner automatically.
- **Other portable candidates:** FastNoise2 for procedural fields/noise, Recast/Detour for native navigation, TinySoundFont for synthesis. These can live behind the native capability boundary and also be used without Unity. Do not add native navigation alongside Unity Navigation without selecting one owner. Existing Unity-specific render/geometry/animation plugins still require Unity; a portable Flecs core does not make the complete app engine-independent.

**Capability readiness:** MudBun hierarchy/basic movement/legs/lean/Boing have existing integrations. Rig constraints, broader physics/contact sensing, navigation, Feel/VFX, spline/building/vegetation generation, handles and weather mostly need runtime adapters rather than new purchases. Physically simulated cloth/ropes/volume liquid and general sound synthesis require additional capabilities. A package's presence is not evidence of a working Ecaty adapter.
